# Test architecture

v3's suite was large (5,400 lines) and asserted little: its e2e tests mostly checked a
return code, and its `unit`/`e2e` markers were applied to nothing. v4's suite is built in
three layers (#133). Each layer has one job and one way of asserting.

```
tests/
  conftest.py          markers by directory, hypothesis profiles
  golden.py            golden-file comparison (layer 2)
  rules_doc.py         renders docs/rules.md from the rules
  scenarios.py         scenario discovery and the scenario.toml format (layer 2)
  strategies.py        hypothesis strategies for justification models (layer 3)
  unit/                layer 1 and layer 3, plus unit tests of the helpers above
    validation/
      builders.py      minimal in-memory validation contexts
      rules/           layer 1: one module per rule
  e2e/
    test_scenarios.py  layer 2: one test per scenario
    scenarios/<name>/  one directory per scenario
```

| Run | Selects |
|-----|---------|
| `poetry run pytest -m unit` | everything under `tests/unit/` |
| `poetry run pytest -m e2e` | everything under `tests/e2e/` |
| `poetry run pytest --update-goldens` | rewrites the golden reports and `docs/rules.md` instead of comparing them |

The marker comes from the directory (`tests/conftest.py`). A test file anywhere else is a
collection error.

## Layer 1: rule unit tests

One test module per validation `Rule` (#118, #119), under `tests/unit/validation/rules/`.

- **Table-driven.** A list of `pytest.param(...)` cases, each a minimal in-memory
  `ValidationContext` built with `tests/unit/validation/builders.py`, and the diagnostics
  it must produce.
- **Assert `Diagnostic.code` and `Diagnostic.severity`, and the element they point at.
  Never a message substring.** Messages are written for humans and will be reworded. Codes
  are the contract.
- Each rule has at least one case that fires and one near-miss that does not.

`docs/rules.md`, the reference of every code, is rendered from the rules by
`tests/rules_doc.py`. `tests/unit/test_rules_doc.py` fails when the committed page differs,
or when a code defined in the package is not on it; `--update-goldens` rewrites it.

## Layer 2: golden JSON reports

Every scenario under `tests/e2e/scenarios/` is run through the CLI. Its **entire** JSON
report (#122) is then compared with the committed `expected.json`. That one assertion pins
statuses, produced values, diagnostics, bindings, ordering and the summary, and any change
in behaviour shows up as a diff in review.

Each scenario runs in a temporary copy of its directory, so nothing it writes (diagrams,
`__pycache__`) lands in the repository. The temporary path is replaced by `<scenario>` in
the report before comparison.

When a change in behaviour is intended, regenerate and review the diff:

```bash
poetry run pytest -m e2e --update-goldens
git diff tests/e2e/scenarios/
```

A scenario with no `expected.json` fails and says how to create it. The golden reports are
generated by the runner and reviewed, never written by hand. Until the CLI exists the
scenario test is skipped; the first golden reports are committed with it, in #124.

### Scenario layout

```
tests/e2e/scenarios/<name>/
  scenario.toml        how to run it, and what it is for
  justification.json   the model, as the jPipe compiler emits it
  steps.py             the step library (or several, or a package; see `libraries`)
  expected.json        the golden report (generated)
  mock/ …              anything the steps read
```

`scenario.toml`:

```toml
description = "One sentence: what this scenario demonstrates."
origin = "v3.6.0:tests/e2e/resources/simple_success"   # or "new in v4"
libraries = ["steps.py"]   # each passed as --library, relative to the scenario directory
python_path = []           # each passed as --python-path
exit_code = 0              # 0 ok · 1 justification failed · 3 validation failed (#124)
exercises = ["exact binding", "Pass outcome"]   # free text, for readers
```

Step libraries are written against the v4 authoring API (#113, #114):
`@evidence` / `@strategy` / `@sub_conclusion` / `@conclusion` with positional ids, and
`Pass` / `Fail` / `Skip` return values. There is no external variable injection (no
`--variable`, no `--config-file`). A step that needs an input reads it from the world,
which in a scenario means a file under the scenario directory.

`justification.json` is compiler output and is kept **verbatim**, including fields the
runner ignores (such as `escaped`). The file's format is the interface (ADR-0001), so the
tests use what the compiler actually emits.

## Layer 3: property tests

`hypothesis` covers the logic where examples are not enough: binding resolution (#115)
and topological ordering (#120). `tests/strategies.py` generates well-formed justification
models in the compiler's JSON format. Its own invariants are tested in
`tests/unit/test_strategies.py`, so a property test that fails points at the code under
test, not at the generator.

The resolver's properties are in `tests/unit/test_binding_properties.py`. They check the
resolver against the rule of ADR-0007 written as a declarative oracle, and against a port
of the compiler's `minimalLink`, so the ids the compiler writes into a step library are
tested to resolve. The ordering's properties arrive with #120.

Profiles are selected with `HYPOTHESIS_PROFILE`:

| Profile | Used by | Settings |
|---------|---------|----------|
| `dev` (default) | local runs | 100 examples |
| `ci` | GitHub Actions | 500 examples, derandomized, so every run explores the same cases |
