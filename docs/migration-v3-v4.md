# Migrating from v3 to v4

v4 is a rewrite of jpipe-runner ([ADR-0002](adr/0002-rewrite-from-scratch.md)), and every
v3 step library needs changes to run on it. This page says what changed, in the order a
port meets it: the step library, then the command line, then the packages. The
[CHANGELOG](../CHANGELOG.md) lists every change; [`concepts.md`](concepts.md) defines the
words used here.

What does not change: the runner still reads the JSON the jPipe compiler writes
(`jpipe process -f JSON`), ids still resolve as in v3 (an exact id or alias, the id
qualified by the justification's name, or a unique tail), and drawing a diagram still needs
Graphviz's `dot` program.

## Before you start

- **v3 stays available.** It is frozen at 3.6.0: pin `jpipe-runner<4` to stay on it, and
  read its documentation at the
  [`v3.6.0` tag](https://github.com/jpipe-mcscert/jpipe-runner/tree/v3.6.0).
- **v4 needs Python 3.11 or later**, as 3.6 did.
- **Port one library at a time**, and check each with `jpipe-runner --dry-run`, which
  imports and validates it without calling any step ([`cli.md`](cli.md#a-dry-run)).

## The step library

### An example

The release example of the jPipe tutorials, as the jPipe compiler generated its library for
v3:

<!-- fmt:off -->
```python
import os
from typing import Any, Callable
from jpipe_runner.framework.decorators.jpipe_decorator import jpipe
from jpipe_runner.framework.decorators.link_decorator import jpipe_link

JpipeProduce = Callable[[str, Any], None]

@jpipe_link("release:e1")
@jpipe(produce=["tests_pass"])
def the_test_suite_passes(produce: JpipeProduce) -> bool:
    """[evidence] The test suite passes"""
    result = os.path.isfile("mock/tests.ok")   # your real check goes here
    produce("tests_pass", result)
    return result

@jpipe_link("release:e2")
@jpipe(produce=["changelog_ok"])
def the_changelog_is_up_to_date(produce: JpipeProduce) -> bool:
    """[evidence] The changelog is up to date"""
    with open("mock/CHANGELOG.md") as f:
        result = "2.0" in f.read()   # the changelog names this release
    produce("changelog_ok", result)
    return result

@jpipe_link("release:s")
@jpipe(consume=["tests_pass", "changelog_ok"])
def all_release_gates_pass(tests_pass: bool, changelog_ok: bool) -> bool:
    """[strategy] All release gates pass"""
    return tests_pass and changelog_ok
```
<!-- fmt:on -->

v4 stops it at its first import, and says what replaced it:

```
ImportError: jpipe_runner.framework is the jpipe-runner 3 authoring API, which jpipe-runner 4 replaced. Import from jpipe_runner instead: @evidence, @strategy, @sub_conclusion and @conclusion replace @jpipe and @jpipe_link, and a step returns Pass(), Fail(reason) or Skip(reason) instead of True or False. A step library generated by jPipe 2.5.0 or earlier is written for jpipe-runner 3: run it with jpipe-runner<4, or update it by hand.
```

The same library on v4, as the [tutorial](tutorial.md) and
[`end-to-end.md`](end-to-end.md) run it. Its first evidence reads the test suite's JUnit
report rather than checking that a marker file exists:

```python
from pathlib import Path
from xml.etree import ElementTree

from jpipe_runner import Fail, Outcome, Pass, evidence, strategy

RELEASE = "2.0"


@evidence("release:e1", observes={"report": "mock/junit.xml"}, produces=["tests_pass"])
def the_test_suite_passes(report: Path) -> Outcome:
    """[evidence] The test suite passes"""
    suite = ElementTree.parse(report).getroot()
    failed = int(suite.get("failures", "0")) + int(suite.get("errors", "0"))
    if failed == 0:
        return Pass(tests_pass=True)
    return Fail(f"{report}: {failed} tests failed")


@evidence("release:e2", observes={"changelog": "mock/CHANGELOG.md"}, produces=["changelog_ok"])
def the_changelog_is_up_to_date(changelog: Path) -> Outcome:
    """[evidence] The changelog is up to date"""
    if RELEASE in changelog.read_text(encoding="utf-8"):
        return Pass(changelog_ok=True)
    return Fail(f"{changelog} does not name release {RELEASE}")


@strategy("release:s", consumes=["tests_pass", "changelog_ok"])
def all_release_gates_pass(tests_pass: bool, changelog_ok: bool) -> Outcome:
    """[strategy] All release gates pass"""
    if tests_pass and changelog_ok:
        return Pass()
    return Fail("a release gate did not pass")
```

### What to change

| v3 | v4 |
|---|---|
| `from jpipe_runner.framework.decorators… import …` | `from jpipe_runner import …` |
| `@jpipe_link("id")` above `@jpipe(consume=[...], produce=[...])` | one decorator for the element's kind, its ids first: `@evidence("id", produces=[...])`, `@strategy("id", consumes=[...], produces=[...])`, `@sub_conclusion(...)`, `@conclusion("id", consumes=[...])` |
| a function without `@jpipe_link`, bound by its name: the element's label in snake case | every step names its element's id; the function's name is free |
| a `produce` parameter, last, and `produce("x", value)` | `return Pass(x=value)` |
| `return True` / `return False` | `return Pass()` / `return Fail("why")` |
| `@skip(...)`, decided when the module is imported | `return Skip("why")`, decided when the step runs |
| `@contribution(...)` | removed: it had no effect |
| a file opened by path inside an evidence | `@evidence(..., observes={"name": "path"})`, received as the parameter `name` |
| a value injected with `--variable` or `--config-file` | produced by a step, or read by a step from a file, a constant or the environment ([ADR-0008](adr/0008-drop-external-variable-injection.md)) |

[`authoring.md`](authoring.md) describes each of these in full.

### What v4 checks that v3 did not

A port that imports cleanly may still be refused by validation, which checks the library
against the model before any step runs, and reports every problem at once. These are the
checks a v3 library most often fails; [`rules.md`](rules.md) describes them all, with
their fixes.

- **Every evidence observes something** (`JP018`): declare the files it reads with
  `observes`. A placeholder that returns `Pass()` is fake evidence.
- **Every evidence produces a value another step consumes** (`JP012`), so that the
  strategy above it judges the facts, not only a verdict.
- **Binding is one to one** (`JP007`): v3 let one function's ids bind several elements.
  Share the code in a helper, and give each element its own step.
- **An id that designates no element is an error** (`JP015`): v3 ignored it, so a typo
  meant the check never ran.
- **A consumed variable is produced by a step that supports its consumer** (`JP014`): v3
  only checked that the producer came earlier, so a consumer on another branch could run
  without its value.
- **A `Pass` carries exactly the values the step declares** (`JP023`, `JP024`).
- **Two libraries cannot have the same file name** (`JP021`): each is imported as the
  module named after its file. v3 silently used the first one's functions.

In the other direction, **a warning no longer fails a run**: v3 counted every warning as
a failure. Only `--strict` counts validation's warnings as errors. A strategy that ignores a value its supporters produce
for another step, an error in v3, is now a warning (`JP013`).

### What behaves differently when the steps run

- **A skip stops what it supports**, as a failure does: everything above it is skipped,
  without being called. In v3, a step skipped with `@skip` let the steps above it run,
  without the values it never produced. A check meant to be optional should pass with
  what it found ([ADR-0021](adr/0021-execution-semantics.md)).
- **A step that raises fails its element, and the run goes on**, so one run reports every
  broken step, each with its traceback (`JP022`). A step that calls `sys.exit()` fails
  the same way, rather than ending the run.
- **A skipped justification is not a failure**: its verdict is `skip`, and the command
  exits 0 unless the run is `--strict`.

## The command line

| v3 | v4 |
|---|---|
| `-v NAME:VALUE`, `--variable NAME:VALUE` | removed. `-v` is now `--verbose` |
| `--config-file FILE` | removed |
| `-V`, `--verbose` | `-v`, `--verbose`; `-vv` for details |
| `-q`, `--quiet`: no ASCII banner | `-q`, `--quiet`: log errors only. There is no banner |
| `-l`, `--library`, optional | `-l`, `--library`, required; a file or a quoted glob |
| `-p`, `--python-path`, the working directory by default | no default: pass `-p .` to import modules from the working directory |
| `-d`, `--diagram PATTERN`, which was ignored | `--diagram PATH`, the file to draw |
| `-f`, `--format`, and `-o`, `--output-path DIR` | the suffix of `--diagram PATH` or `--dataflow PATH` is the format |
| `--dry-run`, which reported a pass | `--dry-run` validates, calls no step, and reports `valid` |
| a justification ending in `.json` | any file name: its content is checked, and a `.jd` file is refused with a fix |

v4 adds `--json` and `--report PATH` (the JSON report), `--dataflow PATH`, `--strict`,
`--colour`, `--version`, and the `impact` and `status` subcommands: [`cli.md`](cli.md)
describes them all.

**Exit codes.** v3 exited 1 for every problem. v4 exits 0 when the justification holds, 1
when it fails, 2 for a usage error, 3 when nothing could run, and 4 when a file could not
be read or written ([Exit codes](cli.md#exit-codes)). A CI script that tested for 1 should
test for anything but 0.

**Output.** v3's ASCII banners and results table are gone: the text report is for people,
and its layout may change. A program reads the JSON report instead, a versioned contract
([`report-schema.md`](report-schema.md)). Diagrams are drawn as the jPipe compiler draws
them, with the run's statuses over them.

## Installing

- **The `graphviz` Python package is no longer needed**, nor is any Python Graphviz
  binding: only Graphviz's `dot` program, for diagrams in any format but `dot`.
- **The `docs` and `full` extras are gone**, with the Sphinx API documentation: the
  documentation is under [`docs/`](README.md). `PyYAML` is no longer a dependency.
- **A step library imports what the runner's Python has installed.** Install
  `jpipe-runner` in your project's environment, beside the packages your steps import;
  the Homebrew, pipx and Ubuntu packages suit libraries that use only the standard
  library ([`cli.md`](cli.md#step-libraries-that-import-packages)).

## Libraries the compiler generates

The jPipe compiler can generate the skeleton of a step library (`jpipe process -f PYTHON`).
As of jPipe 2.5.0, that skeleton is written for v3, as in the example above: port it by
hand ([#140](https://github.com/jpipe-mcscert/jpipe-runner/issues/140)).
